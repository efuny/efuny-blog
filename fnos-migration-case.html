实战复盘 / fnOS

飞牛 OS：从 SD 卡系统迁到 SSD，并处理风险数据盘与 Docker 落盘

这次维护的目标不是单纯“把系统复制过去”，而是在 HP Gen8 的硬件限制下，尽量做到可验证、可回滚、不误伤三块数据盘。 最终方案是：SD 卡继续作为引导入口，Intel SSD 承载真正的系统根目录，风险数据盘先抢救备份，Docker 数据实际落到 SSD。

案例一：系统盘从 SD 卡迁到 SSD

一开始尝试让 Intel SSD 作为独立启动盘，但 HP Gen8 的 SATA5 光驱位没有稳定启动成功。 因此最终改为更稳的结构：SD 卡只负责 GRUB，引导后把根目录切到 SSD。

1. 先确认盘位和当前根分区

这一组命令全部是只读检查，用来避免把数据盘当成系统盘操作。

lsblk -f
blkid
findmnt /
lsblk -o NAME,SIZE,MODEL,SERIAL,TRAN,FSTYPE,UUID,MOUNTPOINTS

当时确认到的关键结论：

  • sda/sdb/sdc 是数据盘，分别挂载到 /vol2、/vol3、/vol1。
  • Intel SSD 是 INTEL SSDSC2BW120A4，稳定设备名为 /dev/disk/by-id/ata-INTEL_SSDSC2BW120A4_CVDA433403NE1207GN。
  • SD 卡和旧克隆 SSD 一度存在重复 UUID，所以后续全部以 UUID 和 by-id 做判断，不信任 /dev/sdX 顺序。

2. 初始化目标 SSD

旧克隆分区只读挂载失败，因此直接初始化 Intel SSD，重新建一个干净的 ext4 根分区。

TARGET="/dev/disk/by-id/ata-INTEL_SSDSC2BW120A4_CVDA433403NE1207GN"

sudo wipefs -a "$TARGET"
sudo dd if=/dev/zero of="$TARGET" bs=1M count=16 conv=fsync

sudo parted -s "$TARGET" mklabel msdos
sudo parted -s "$TARGET" mkpart primary ext4 1MiB 100MiB
sudo parted -s "$TARGET" mkpart primary ext4 100MiB 100%
sudo parted -s "$TARGET" set 2 boot on
sudo partprobe "$TARGET"

sudo mkfs.ext4 -F -L fnos-root-ssd "${TARGET}-part2"

新根分区 UUID：

e3f4bb3d-db76-429a-95d9-694c54c4535b

3. 复制系统到 SSD

复制时排除了运行时目录、挂载点和数据卷，避免把 /vol1、/vol2、/vol3 的内容带进系统盘。

SSD_UUID="e3f4bb3d-db76-429a-95d9-694c54c4535b"
SSD_MNT="/mnt/fnos-root-ssd"

sudo mkdir -p "$SSD_MNT"
sudo mount UUID="$SSD_UUID" "$SSD_MNT"

sudo rsync -aAXHSx --numeric-ids --info=progress2 \
  --exclude="/dev/*" \
  --exclude="/proc/*" \
  --exclude="/sys/*" \
  --exclude="/tmp/*" \
  --exclude="/run/*" \
  --exclude="/mnt/*" \
  --exclude="/media/*" \
  --exclude="/lost+found" \
  --exclude="/vol1/*" \
  --exclude="/vol2/*" \
  --exclude="/vol3/*" \
  --exclude="/swapfile" \
  / "$SSD_MNT"/

4. 写入 SSD 的 fstab

printf 'UUID=%s / ext4 errors=remount-ro 0 1\n/swapfile none swap sw 0 0\n' "$SSD_UUID" | sudo tee "$SSD_MNT/etc/fstab"

5. 测试 SSD 独立启动，并保留回滚

这一步只把 GRUB 安装到 Intel SSD，不改 SD 卡。失败时插回 SD 卡即可回退。

sudo mount --bind /dev "$SSD_MNT/dev"
sudo mount --bind /proc "$SSD_MNT/proc"
sudo mount --bind /sys "$SSD_MNT/sys"
sudo mount --bind /run "$SSD_MNT/run"

sudo chroot "$SSD_MNT" /usr/sbin/grub-install --target=i386-pc --recheck /dev/sdd
sudo chroot "$SSD_MNT" /usr/sbin/update-grub

验证 SSD 上的 GRUB 已经指向新 UUID：

sudo grep -R -n -E "root=UUID=|search.*fs-uuid" "$SSD_MNT/boot/grub/grub.cfg" | head -80

测试结果：SATA5 独立启动失败，因此切换到 SD 卡引导、SSD 运行根系统的方案。

6. SD 卡引导，SSD 作为真正根目录

这里不能把 search --fs-uuid 全部替换掉，因为它负责让 GRUB 从 SD 卡找到 /boot/vmlinuz 和 initrd。 正确做法是只改 Linux kernel 参数里的 root=UUID=...。 

OLD_UUID="3be0b1af-df86-4bac-8995-45e862d2dbd1"
SSD_UUID="e3f4bb3d-db76-429a-95d9-694c54c4535b"

sudo cp /boot/grub/grub.cfg "/boot/grub/grub.cfg.sd-to-ssd-root.bak.$(date +%Y%m%d-%H%M%S)"
sudo sed -i "s/root=UUID=${OLD_UUID}/root=UUID=${SSD_UUID} rootdelay=10/g" /boot/grub/grub.cfg

sudo grep -R -n -E "search.*fs-uuid|root=UUID=" /boot/grub/grub.cfg | head -80
sync
sudo reboot

成功验证：

findmnt /
lsblk -f /dev/sdd /dev/sde

重启后虽然盘符顺序变化，但 UUID 指向 e3f4...，确认 / 已经在 Intel SSD 上。

案例二：数据盘 1 有 SMART 风险，先迁数据

风险盘是 WD-WCAV5M641288，对应 /vol1。SMART 显示整体仍为 PASSED，但已经有 Reallocated_Sector_Ct = 1 和 Current_Pending_Sector = 1。

1. 确认风险盘和文件系统状态

lsblk -o NAME,SIZE,MODEL,SERIAL,TRAN,FSTYPE,UUID,MOUNTPOINTS
ls -l /dev/disk/by-id/ | grep 'WD-WCAV5M641288'

DISK="$(readlink -f /dev/disk/by-id/*WD-WCAV5M641288* | head -1)"
sudo /usr/sbin/smartctl -a "$DISK" | grep -E 'SMART overall|Reallocated_Sector_Ct|Current_Pending_Sector|Offline_Uncorrectable|UDMA_CRC_Error_Count|Power_On_Hours|# 1|# 2|# 3'

sudo btrfs device stats /vol1
sudo btrfs device stats /vol2
sudo btrfs device stats /vol3

判断逻辑：

  • SMART 有待映射扇区，说明盘已经出现不稳定信号。
  • Btrfs stats 全 0，说明文件系统还没记录读写错误，不应该马上做破坏性修复。
  • 优先级是迁走数据，而不是修盘。

2. 先看 /vol1 顶层占用

sudo du -h -d1 /vol1 2>/dev/null | sort -h
sudo du -sh /vol1/docker /vol1/@appmeta /vol1/@appdata /vol1/@appconf /vol1/@appcenter 2>/dev/null
df -h / /vol1 /vol2 /vol3

关键结果：

  • /vol1/1000 约 140G，是最重要的用户数据。
  • /vol1/docker 约 29G，是大量小文件和容器数据。
  • /vol2 基本空闲，适合作为临时承接盘。

3. 把关键数据复制到 /vol2

DEST="/vol2/vol1-migration-$(date +%Y%m%d)"
sudo mkdir -p "$DEST"

sudo rsync -aHAX --numeric-ids --info=progress2 /vol1/1000/ "$DEST/1000/"
sudo rsync -aHAX --numeric-ids --info=progress2 /vol1/@appdata/ "$DEST/@appdata/"
sudo rsync -aHAX --numeric-ids --info=progress2 /vol1/@appmeta/ "$DEST/@appmeta/"
sudo rsync -aHAX --numeric-ids --info=progress2 /vol1/@appcenter/ "$DEST/@appcenter/"
sudo rsync -aHAX --numeric-ids --info=progress2 /vol1/@sysappmeta/ "$DEST/@sysappmeta/"

du -sh "$DEST"/*
df -h /vol1 /vol2 /

完成后的结果：

/vol2/vol1-migration-20260619/1000          140G
/vol2/vol1-migration-20260619/@appdata      1.1G
/vol2/vol1-migration-20260619/@appmeta      3.7G
/vol2/vol1-migration-20260619/@appcenter    2.6G
/vol2/vol1-migration-20260619/@sysappmeta   8.7G

案例三：Docker 从机械盘迁到 SSD，并兼容飞牛应用中心

Docker 原来在 /vol1/docker，也就是风险盘上。直接把 Docker 配置改成 /opt/docker 可以运行， 但飞牛应用中心只认存储空间 1/2/3，重启后会把配置改回 /vol2/docker 这样的路径。

1. 查 Docker 当前配置

sudo docker info | grep -E 'Docker Root Dir|Storage Driver'
sudo cat /etc/docker/daemon.json
sudo docker ps --format 'table {{.Names}}\t{{.Status}}'
du -sh /vol1/docker
df -h / /vol1

2. 冷迁移 Docker 数据到 SSD

NEW_ROOT="/opt/docker"
OLD_ROOT="/vol1/docker"
BACKUP_ROOT="/vol1/docker.bak.$(date +%Y%m%d-%H%M%S)"

sudo systemctl stop docker
sudo mkdir -p "$NEW_ROOT"
sudo rsync -aHAX --numeric-ids --info=progress2 "$OLD_ROOT"/ "$NEW_ROOT"/

sudo cp /etc/docker/daemon.json "/etc/docker/daemon.json.bak.$(date +%Y%m%d-%H%M%S)"
sudo mv "$OLD_ROOT" "$BACKUP_ROOT"

3. 最终方案：/vol2/docker 是外观路径，/opt/docker 是真实落盘

飞牛继续认为 Docker 在 /vol2/docker，但这个目录通过 bind mount 指向 SSD 的 /opt/docker。

sudo systemctl stop docker.socket docker
sudo mv /vol2/docker "/vol2/docker.empty.$(date +%Y%m%d-%H%M%S)" 2>/dev/null || true
sudo mkdir -p /vol2/docker
sudo mount --bind /opt/docker /vol2/docker

让 daemon.json 保持飞牛能接受的路径：

sudo python3 - <<'PY'
import json
path = "/etc/docker/daemon.json"
with open(path) as f:
    data = json.load(f)
data["data-root"] = "/vol2/docker"
with open(path, "w") as f:
    json.dump(data, f, indent=4, ensure_ascii=False)
    f.write("\n")
PY

4. 用 systemd 持久化 bind mount

sudo tee /etc/systemd/system/vol2-docker.mount >/dev/null <<'EOF'
[Unit]
Description=Bind SSD Docker data to /vol2/docker
Before=docker.service
After=local-fs.target
RequiresMountsFor=/opt/docker /vol2

[Mount]
What=/opt/docker
Where=/vol2/docker
Type=none
Options=bind

[Install]
WantedBy=multi-user.target
EOF

sudo mkdir -p /etc/systemd/system/docker.service.d
sudo tee /etc/systemd/system/docker.service.d/10-require-ssd-bind.conf >/dev/null <<'EOF'
[Unit]
Requires=vol2-docker.mount
After=vol2-docker.mount
EOF

sudo systemctl daemon-reload
sudo systemctl enable vol2-docker.mount
sudo systemctl start docker

5. 重启后验证

findmnt /
findmnt /vol2/docker
sudo docker info | grep 'Docker Root Dir'
sudo docker ps --format 'table {{.Names}}\t{{.Status}}'
systemctl status vol2-docker.mount --no-pager
df -h / /vol1 /vol2

成功标准：

/vol2/docker -> /dev/sde2[/opt/docker]
Docker Root Dir: /vol2/docker
vol2-docker.mount active (mounted)

回滚点和风险控制

  • 系统盘迁移前，不格式化 SD 卡；SSD 独立启动失败后仍能回到 SD 卡引导。
  • 修改 SD 卡 GRUB 前备份 /boot/grub/grub.cfg，只替换 kernel 参数里的 root=UUID。
  • 风险盘不做 btrfs check --repair，先把用户数据和应用元数据复制到健康盘。
  • Docker 迁移后保留 /vol1/docker.bak.20260619-150838，确认稳定几天再删除。
  • 飞牛应用中心会重写 Docker 存储路径，所以最终用 bind mount 兼容它的路径假设。
